# 附近联机三端对等 UX 设计

日期：2026-09-23。此设计记录用户对附近联机体验和范围的最新要求；
`docs/nearby/DESIGN.md` 描述 2026-09-21 的 Android 房主到 HarmonyOS 客机可玩基线，
不再限定下一阶段的角色和网络范围。

2026-09-23 评审通过。实施必须采用测试先行的红、绿、重构流程，改动范围限于
三端原生 UX、布局、文案和对既有联机后端接口的调用。不得更改共享协议、会话
状态机、加密、传输、模拟器或游戏逻辑；缺失的平台接线须与真正的后端行为分开
记录，不允许用演示二维码、静态“已连接”或不可用按钮冒充成功。

2026-09-23 补充决定：本轮不新增缺失的平台联机桥，也不以当前桥接范围限制
前端角色入口。三端均显示创建和扫码；后端未接通的操作进入正式页面并给出
真实失败原因。下面涉及三端全组合可玩、自动热点及网络回退的目标，在本轮
分别按实际接线和模拟器证据验收；不能把前端页面通过当作这些能力已实现。

2026-09-25 用户修订：扫码连接成功即进入空房间，不再有“确认入局”步骤。
房主从现有游戏大厅明确选择游戏；客机只匹配本机相同 ROM。匹配成功后双方
自动准备并开局，不再要求额外点击确认。房主回大厅选择另一款游戏时，
双方保留当前连接和座位，直到主动断开或会话实际结束。

## 目标与现状

Android、HarmonyOS NEXT、iOS 的任意一端都可以创建房间或扫码加入。
房主是 P1，客机是 P2；座位由本次操作决定，与操作系统无关。
两台设备可接入同一路由器的局域网，也可由一台设备提供热点、另一台加入。
两种网络共用同一邀请二维码、连接和选游戏流程，不向用户提供额外的“模式选择”向导。
优先使用已连接的局域网；没有可用局域网时，Android 房主在原页面自动尝试
创建本地专用热点，其余情况在原页面引导用户建立热点网络。
范围按三端之间的所有有序组合设计，包括同平台的两台设备。

当前可玩软件路径只有 Android 建房和 HarmonyOS 扫码。共享 LAN MVP ABI
已有 host/join 操作，但 Android 客机、HarmonyOS 房主以及 iOS 两种角色尚未
完成产品接线；iOS 附近页面目前是不可联机的占位 UI。因此本设计是目标，
不能据此称三端对等联机已实现。

## 页面路径

1. 三端游戏大厅均保留一个“附近联机”入口。进入后只显示两个同等清晰的选择：
   “创建房间”和“扫码加入”，并用一行文字说明两端须在同一个本地网络。
2. 点“创建房间”直接进入邀请页，网络就绪后生成二维码。点“扫码加入”立即打开本机相机
   扫码器；权限请求仅在首次使用相机时出现。扫码取消返回角色选择页，扫码成功
   才呈现连接状态。连接失败在当前状态页给出原因与“重新扫码”，不跳进另一页。
3. 建立连接后进入空联机房间。房主在现有游戏库选择或更换游戏，客机读取本机
   相同内容。页面只显示连接状态、P1/P2、游戏名称、内容匹配结果和准备状态。
   内容匹配后两端自动准备并开局，不显示确认入局操作。暂停、回房间与同一连接内换游戏继续沿用现有路径。
   任一方主动断开或会话实际结束时，两端退出房间并回到“附近联机”角色入口；
   只离开房间页面或进入其他应用页面不等于断开。再次打开附近联机时，若仍有
   活跃会话，优先回到同一房间；回房间换游戏须沿用原连接，不能重新扫码。
4. 配对只保留二维码一种方式。好友、蓝牙/附近设备发现、六位配对码的入口、
   页面、设置项、占位操作及只为这些功能服务的产品代码全部移除；不以可点击
   按钮和“暂不支持”提示占用横屏空间。共享层中若有其他会话功能仍依赖的协议
   类型，先验证依赖再删除，不能为了界面清理破坏现有单机和可玩联机路径。

## 横屏布局

- 角色选择页：中部两张等宽大卡片，左侧创建、右侧扫码；顶部只有返回与标题。
- 邀请页：左侧是尽可能大的正方形二维码，右侧依次放标题、网络说明、
  当前自动选用的本地网络状态与“重新生成二维码”。自动热点时右侧显示
  热点名称与密码，让客机先接入该网络再扫码。返回键只离开页面，明确的
  “断开”操作才结束邀请或会话。不设底部按钮栏或日常网络模式选择器。
- 连接状态页：清楚显示验证/连接进度与取消；失败原因在同一位置替换状态文字。
- 联机房间：左侧连接与座位，右侧游戏与本端唯一主要操作。诊断数据留在日志，
  不做逐页翻看的用户界面。
- 应用自有的附近联机页面在横屏可用高度内呈现，不依赖上下或左右滑动；
  不出现任何应用内滚动条。布局按安全区域后的实际宽高分配空间，二维码保持
  正方形，左右区域随宽度调节；文字按系统字号同比例变化，不单独缩小按钮文字
  或固定绝对高度造成字体、卡片和按钮比例失调。高度不足时优先省略可选说明，
  再压缩空白与二维码尺寸，主要操作和至少 48dp 的触控目标始终完整可见。
  iOS 现有 `ScrollView` 和底部固定确认栏需要按此重排。

## 网络与失败状态

应用读取可用于本地联机的网络接口，房主二维码包含本次选用网络的可达地址。
先选已经连接且有可用本地地址的路由器 Wi-Fi/以太网局域网；不要求它能访问互联网。
没有这类局域网时，如果本机热点网络已可用，改用热点地址。若热点也未开启，
Android 房主自动请求创建本地专用热点：仅在需要时请求 Wi-Fi 权限，在邀请页显示
“正在创建本地热点”；收到系统就绪回调并确认可监听的本地地址后，才生成邀请二维码。
本地专用热点不提供互联网，正好用于本产品的离线联机；它与系统的共享上网热点
不是同一种开关。将系统返回的热点名称和密码显示在邀请页，并提示客机先加入该网络。
用户不需要经过热点模式选择页。

Android 当前 `minSdk 24`、`targetSdk 36`：本地专用热点 API 从 Android 8.0
（API 26）可用。实现时声明 `CHANGE_WIFI_STATE`；Android 13 及更高版本按目标
SDK 请求 `NEARBY_WIFI_DEVICES`，较早系统请求 `ACCESS_FINE_LOCATION`。
如系统拒绝授权、设备低于 API 26、热点启动失败或与共享上网冲突，在同一邀请页
说明原因，并提供系统手动开热点的指引与“重新检测”。HarmonyOS 和 iOS 房主
暂用同页手动热点引导；这不改变三端都能建房、都能加入的产品目标。

Android 自动热点的 reservation 属于联机会话，不属于邀请页：进入房间或游戏时
仍保持，结束会话时释放。若系统提前停止热点，立即使当前邀请失效并提示重建。
若有多个候选，仍按局域网优先、热点其次的顺序自动选择，不要求用户先选模式。
用户在局域网连接失败后选择“改用热点”时，旧邀请作废；Android 房主自动尝试
本地专用热点，其他房主按同页指引开启热点，热点就绪后生成新二维码。应用不
绕过系统权限；热点所有者与房主角色不作平台绑定。

本机已连局域网只能证明候选网络存在，不能证明另一台设备可达。扫码后以实际
加密连接作为判断依据；如果局域网连接失败，在原状态页提示确认两端在同一网络、
检查路由器的设备隔离，并提供“改用热点”引导。切换网络后房主生成新二维码，
客机重新扫码。邀请过期、扫码无效和游戏内容不匹配也显示具体原因与当前页
可执行的下一步。

邀请码仍是一次性的，保留现有 TLS pin、内容摘要和双方就绪的协议校验；二维码载荷
不得出现在界面以外的日志中。不增加云端配对、ROM 传输或持久好友数据。

## 验收标准

- 三端都能通过各自的“创建房间”展示真实可用二维码，也都能在点“扫码加入”
  后立即进入扫码器；没有配对说明中转页。
- 三端的房主/客机角色与 P1/P2 显示和实际输入归属一致，联机流程不按平台分支。
- 一方断开后双方均回到联机入口；普通页面离开保留会话；同一会话能连续游玩
  多个游戏。此条必须用真实双机状态验证，单机模拟器只验证页面跳转与生命周期。
- 同一路由器局域网和个人热点两种网络都能完成扫码、连接、同一游戏自动准备、
  双人输入与回房间换游戏。验证覆盖三端有序配对组合；构建或模拟结果不替代
  两台真实设备的可玩证据。
- 有局域网时默认选它；没有局域网时 Android 房主自动尝试本地专用热点，其他
  房主显示手动热点引导；热点未就绪不显示无效二维码。局域网实际连不通时给出
  同网检查与热点切换，不声称自动证明网络互通。
- Android 自动热点在权限获准且设备支持时能建立房间、显示真实热点凭据并让
  第二台设备连接；权限拒绝、API 24–25、系统启动失败均在同页有可操作的回退。
- 横屏页面无应用内四向滑动；二维码和主要操作不被底部栏、系统安全区或文字放大遮挡。
- Android、HarmonyOS、iOS 均须在可用模拟器上检查短横屏、宽横屏和放大字体，
  保存布局证据；模拟器只证明界面与软件交互，真实双机可玩另行验证。
