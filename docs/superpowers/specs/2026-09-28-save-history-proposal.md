# 可回退存档系统方案（已授权实施）

日期：2026-09-28。长期范围为三端单机游玩。用户已授权分支、worktree 与 TDD 实施，并在 Mac 不可达后明确“先做鸿蒙安卓”；本次交付范围为 Android 与 HarmonyOS NEXT，iOS 接入及原始 iPhone 通关现场验收后续进行。具体完成状态以验证报告为准。

## 目标

自动留下多个游玩恢复点，用户通过截图和时间找到想回去的位置。恢复旧进度、重新开始都先保护当前进度。已存在的单槽自动存档迁移后仍可恢复。

## 方案选择

| 方案 | 收益 | 限制 |
| --- | --- | --- |
| 按游玩时间自动存档（推荐首版） | 可复用现有快照能力，不依赖游戏关卡信息 | 不能保证恰好在关卡起点或死亡前保存 |
| 时间存档 + 已适配游戏的关卡存档（后续） | 支持的 ROM 可精确回到关卡起点，其他游戏使用时间存档 | 需要按 ROM 版本验证关卡识别规则，不能宣称所有游戏支持 |
| 画面变化推测关卡 | 不需要逐游戏读取状态 | 菜单、死亡、闪屏均可能误判；不作为正式关卡存档依据 |

当前 `nes_*` / `fly_runtime_*` 接口提供游戏状态保存与恢复，没有通用关卡事件。后续关卡适配须按 ROM 内容哈希匹配，规则放在数据/适配资源中，遵守产品代码不硬编码内置游戏的约束。未知版本自动回退到时间存档，页面明确显示当前策略。

## 首版交互

- 暂停菜单提供“继续游戏”“存档记录”“保存当前进度”“重新开始”“游戏中心”“设置”。具体排序和小屏滚动在平台布局阶段验证。
- 游戏中心仅保留“继续游戏 / 开始游戏”主按钮，依据可恢复存档状态显示；按用户 2026-09-28 最新反馈，移除其附近的“存档记录”“从头开始”按钮，这两个功能只在游戏内暂停菜单提供。
- 存档列表包含截图、保存日期时间、本轮游玩时长、类型（自动/手动/回退前/重开前/旧版迁移）和备注。未识别关卡时不显示虚构关卡号。
- 选择记录后展示预览，再确认恢复；完成后保持暂停，用户点继续开始运行。
- 手动记录可命名、删除；自动记录可标记为保留。删除须明确对象，不批量清理用户保护的记录。
- 回退后旧历史仍保留，并标记“从此存档继续”。列表同时区分保存时间与该局进度时间，避免回退后的时间顺序误导。
- 重新开始建立新一局，保留历史；下次继续恢复新一局，用户仍可从记录返回重开前。

## 自动保存与保留规则（建议默认值）

- 默认每实际运行 1 分钟保存一次，可选 30 秒、1 分钟、2 分钟、5 分钟或关闭。
- 时钟使用前台、模拟器实际运行的累计时间；暂停、后台和存档操作不计时。首版无法通用识别游戏内菜单或游戏自身暂停，这些运行中的画面仍可能计时和保存。
- 打开暂停、正常退出及平台提供可处理的后台通知时额外保存；同一运行位置的重复触发合并。强制终止或系统未提供执行时间时不能保证最后一刻保存。
- 每游戏保留最近 60 条普通自动记录，跨应用重启保留；因此长时间运行仍会淘汰早期自动点。界面解释此规则，重要记录可手动保护。
- 每游戏建议容量上限 256 MiB、全库建议 1 GiB，实施时用实际快照大小与设备测量复核默认值。按先旧后新清理未保护的自动记录；手动、标记保留和最近一次回退/重开保护点不参与自动淘汰。
- 达到容量或设备空间不足且无可淘汰记录时，停止新增保存并提示管理空间；不静默删除保护记录，也不显示保存成功。
- 最近一次“回退前/重开前”保护点独立保留；下次操作须先可靠写好新的保护点才能替换。需要长期保存的旧保护点可转为手动记录。
- 关闭定时/自动存档不影响读取已有记录；用户主动保存、回退前保护和重开前保护仍可执行。

## 恢复与失败处理

1. 暂停推进，清空正在按下的按钮，在串行核心执行边界捕获当前状态；可靠保存为保护点。
2. 检查目标记录的 ROM 内容标识、快照格式版本与完整性。相同标题不代表同一 ROM。
3. 加载目标记录并清理旧音频、视频与输入队列。存档恢复失败时尝试恢复保护点；仍失败则保持暂停，保留磁盘数据并显示重试入口。
4. 目标恢复及“当前继续位置”持久化都完成后才提示成功；以后启动依据当前继续位置，而不是简单选择创建时间最新的记录。
5. 目标不可用、备份失败、空间不足时不覆盖现有存档。截图失败可用占位图，不应把有效状态误判为保存失败。

保存过程先捕获同一帧的状态与画面，再用不可变副本执行文件写入。状态文件和索引的提交顺序必须支持中途退出恢复；在新记录可靠提交后才清理旧记录。截图可异步完成，但不能截取另一个游玩时刻的画面冒充该存档。

## 独立组件方向（按 9 月 28 日用户补充调整）

- 存档历史作为可单独构建、安装和消费的 C++17 库实现，提供稳定 C ABI。建议目录 `libs/save_history/`，不依赖 `core/`、`shared/`、FlyNES 的游戏目录模型或任何平台 UI。
- 独立库只接收应用提供的不透明状态字节、可选截图字节和通用元数据，负责记录、查询、保护、淘汰、校验和持久化。库内不调用 `nes_*` / `fly_runtime_*`，不持有模拟器实例。
- `shared/` 的适配层管理游戏身份映射、当前游戏设置、自动存档触发、停帧捕获、实际恢复与 UI 结果转换。关卡识别属于适配能力；只向库提供可选标签。
- 建议采用 SQLite 作为库的私有存储依赖；首版优先将元数据、状态 BLOB 和缩略图放入同一数据库，降低多文件一致性复杂度。用真实快照和三端设备验证延迟/体积，再决定是否需要外置大对象。SQLite 的事务不能同时回滚内存中的模拟器，恢复操作仍须外部协调。
- SQLite 类型和表结构不泄漏到公共 API；首版只实现一个实际后端，不先建设多数据库框架。保持同一句柄串行调用，调度由调用方负责；平台现有核心执行所有权不变。
- 详细现状、开源候选、取舍及独立验收标准见 [独立存档库调研](../../verification/2026-09-28-save-library-research.md)。本次仅调整方案，未引入依赖或改变现有存档。
- 记录包含 ID、ROM 内容指纹、游戏目录 ID、快照版本、创建时间、运行时长、来源记录、新一局标识、类型、保护标记、大小与校验、截图引用、备注。
- Android 当前使用直接核心存档，iOS/Harmony 使用运行时 checkpoint；保留各自格式标识和解码路径，不能假定字节兼容。首版不提供跨平台导入或云同步。
- 原有自动存档复制为“旧版进度”记录，验证可读后发布索引；迁移幂等，失败保留原文件。不以删除旧档作为迁移起点。
- 游戏原生电池存档和模拟器快照区分处理。重开保留用户持久化数据；不得直接采用会清空电池缓存的接口而未核实其语义。回退时原生存档状态必须与所恢复的核心状态一致，下一次写回遵循现有持久化规则。
- 联机不接入本地单方回退。联机同步恢复属于单独需求，本次不改其行为。

## 验收

- 先写失败测试：计时触发、暂停不计时、重复触发合并、60 条保留、容量淘汰不触碰保护记录、保护点失败拒绝回退。
- 快照恢复真实运行状态；回退后旧历史仍在，退出重启继续所选分支；重新开始后不重新载入旧结局。
- 覆盖写入/索引提交被中断、坏档、ROM 不匹配、格式不兼容、空间不足和旧档迁移失败。
- 三端按受影响范围运行仓库要求的测试；iOS 真机验证用户反馈的游戏能够重开，并从历史恢复实际可玩进度。
- 测量自动捕获时的停帧、音频中断和空间增长；未经实测不宣称无卡顿或固定空间占用。
- 所有测试用隔离数据；未经授权不清理、覆盖用户现有存档。

首版产品范围建议为“时间自动存档 + 手动保存/回退 + 重开保护”，关卡识别作为后续按 ROM 适配的增强能力。组件独立性是用户明确要求；SQLite 与 BLOB 布局已用于安卓、鸿蒙实现，验证与限制见 `docs/verification/2026-09-28-save-history-android-harmony.md`。iOS 后续接入。
