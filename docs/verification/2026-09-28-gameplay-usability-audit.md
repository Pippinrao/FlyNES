# 游戏游玩体验梳理：重新开始与进度管理

日期：2026-09-28。代码基线：`main@78057350`。本次为代码审查和待实施建议，未修改产品代码、存档或版本，未运行产品测试，也未实机复现用户存档。

用户反馈：iPhone 上《爆炸俄罗斯方块》通关后一直显示通关界面，无法从头开始。具体 ROM 版本、游戏内结局返回操作和该存档内容尚未核验。

## 1. 当前问题与证据

已确认产品缺少重新开始入口，并且默认启动会恢复自动存档。这足以解释“退出再进入仍是同一画面”的路径；是否还叠加游戏自身结局逻辑，需要用用户当前版本和存档复现。

| 发现 | 代码证据 | 结论边界 |
| --- | --- | --- |
| 共享暂停菜单只有继续、游戏中心、设置 | `shared/include/flynes/product/pause_actions.hpp:8`；`shared/tests/test_product_pause_actions.cpp:20` | 当前测试还固定要求三项，属于既有产品能力缺口 |
| iOS 加载 ROM 后恢复自动存档 | `ios/app/run/RunSurfaceViewController.mm:190`、`:356` | 自动存档开启且包含结局时，可再次回到结局 |
| iOS 已有 `resetGame:`，但没有用户菜单入口 | `ios/app/run/RunSurfaceViewController.mm:782`；同文件暂停菜单从 `:464` 构建 | 方法存在不等于用户能重开；该方法还明确排除联机 |

## 2. 优化点与可能痛点

优先级含义：P0 为当前阻断；P1 为进度可信度和常见流程；P2 为操作体验增强。代码缺口、风险推断和需求候选分开标注，不将候选功能描述为已发生故障。

| 优先级 | 痛点 / 场景 | 现状判断 | 优化建议 |
| --- | --- | --- | --- |
| P0 | 通关、Game Over、卡死后无法主动重开 | 已确认：三端无重开入口；用户已报告 iOS 结局受困 | 暂停菜单增加“重新开始”，游戏详情同时提供“从头开始” |
| P1 | 点“继续”却回到标题，不知道进度是否丢失 | 已确认：按钮仅取决于是否玩过 | 根据可用存档显示“继续游戏 / 开始游戏”；恢复失败明确说明 |
| P1 | 不知道保存成功没有，退出时不放心 | 已确认：Android 保存与恢复异常主要写日志；iOS/Harmony 有暂停内保存失败提示 | 显示最近保存时间、成功/失败状态；失败提供重试，退出前说明后果 |
| P1 | 死亡或通关状态覆盖唯一恢复点 | 已确认：用户路径主要是每游戏一个自动槽，没有手动存读档入口 | 增加一个独立手动槽和覆盖提示；自动槽保留上一份可回退版本 |
| P1 | 关闭“自动存档”后，原来的进度也不恢复 | 已确认：三端同一开关同时控制自动写入和自动恢复 | 拆分“是否保存”和“本次从哪里启动”；解释旧存档仍被保留 |
| P1 | 按暂停、系统返回、切后台，保存结果因平台而异 | 已确认调用差异，实际丢档范围待复现 | 统一暂停/离开/后台的保存契约，保证原生停帧后再捕获 |
| P1 | HarmonyOS 直接返回或切后台可能丢失本轮进度 | 代码风险：单机 `onBackPress` 返回 false；页面隐藏/销毁没有保存；Ability 后台回调仅日志；当前保存调用在暂停菜单内 | 用隔离存档验证直接返回与后台被回收，再补齐生命周期保存 |
| P1 | 坏档后突然从头开始，没有解释或恢复入口 | 已确认处理差异：Harmony 隔离坏档并记录日志；Android 恢复返回码仅记录；iOS 记录失败状态 | 保存失败文件，提示恢复未成功，提供重试、上一份存档、从头开始 |
| P1 | 误点重开后想撤销；重开后退出又回到旧结局 | 重开功能引入时必须防止的风险 | 重开前保留恢复点，取消无副作用；新会话成功后更新自动恢复点，失败保留旧档 |
| P2 | 动作游戏同时按方向+A/B容易误触，连续攻击疲劳 | 体验候选；已有自定义布局和 Android 按键映射，不能认定完全不支持 | 在已有布局上验证多指、斜向、滑出取消；按游戏保存布局，评估可选连发 |
| P2 | 外接手柄切换平台后操作不同 | Android 已有基础按键映射；三端完整手柄体验尚未验收 | 实测连接、映射、暂停键和断开释放；据结果补齐统一行为 |
| P2 | 重复开场/练习失败段耗时 | 需求候选；本次产品入口检索未发现快进/倒带/练习槽 | 手动存档优先；再评估按住快进、短时倒带的资源成本 |
| P2 | 切回游戏立即运行，角色来不及反应 | 生命周期体验风险，需逐平台实测 | 返回时保持暂停，让用户明确继续；声音、画面、输入一起恢复 |
| P2 | 不知道 Start、Select、游戏内暂停与模拟器暂停的区别 | 新手体验候选 | 增加可关闭的首次操作提示；游戏说明由内容元数据提供，产品源代码不硬编码游戏名 |

保存差异补充：Android 打开暂停抽屉时停帧，但 `writeAutosave` 在 Activity `onPause`；iOS 打开抽屉和失去前台时写入；HarmonyOS 当前在 `openPause` 内写入。原子写入可以防止半写文件，不能替代可回退的历史存档。

## 3. 建议先落地的范围

推荐“明确区分继续与重开”的方案：单机暂停菜单加“重新开始”，游戏详情保留主按钮并加次级“从头开始”。重开语义为重新启动当前 ROM、跳过自动快照恢复；保留游戏原生电池存档、收藏、封面和游玩历史。对有原生存档的游戏，重新启动只承诺回到启动流程，新建游戏仍遵循游戏自身菜单。

三种方案比较：

1. **推荐：显式重开 + 原进度保护。** 用户能理解，适用于所有 ROM，需要贯通菜单、会话与保存逻辑。
2. **仅加暂停内重开按钮。** 改动较小，但大厅仍无法选择启动方式，“继续”文案和旧档重新恢复问题仍需处理。
3. **自动判断通关后重开。** 不推荐：当前没有已确认的通用通关信号；不同 ROM 结局逻辑不同，误判会打断游玩，也不能在产品源码逐个硬编码游戏。

建议重开流程：

1. 用户点“重新开始”，显示确认：将返回游戏启动画面，当前进度会先保留。
2. 取消时保留暂停状态；确认后停止帧循环和音频，释放所有按键。
3. 可靠保留当前恢复点；保留失败时显示错误，不能假装已备份并继续覆盖。
4. 重新加载当前 ROM，显式跳过旧自动快照，清理旧音频与画面队列。
5. 新会话和恢复点保存成功后再恢复播放；后续退出重进应继续新一局。
6. 失败保留原进度并允许重试；提供恢复重开前进度的可达入口。

首批实施建议拆为：先完成三端单机重开及回退保护；随后修正“继续”判定、保存状态与生命周期差异；最后评估连发、快进、倒带等增强功能。上述为待确认方案，不表示已实现。

附近联机不在本次实施范围内；当前 iOS 重置方法明确拒绝联机。不能把单机重开按钮直接开放给联机，否则可能导致双方状态不一致。若后续纳入，应单独定义发起权限、双方同步重置和失败反馈。

## 4. 实施时的验证要求

- 先用隔离存档做失败断言：存在旧进度时，用户选择重开必须进入新会话；取消不改变原进度。
- iOS 验证重开后暂停、后台、退出再进不恢复旧结局；验证备份/重新加载/写新存档失败仍能找回旧进度。
- 使用用户反馈的 ROM 版本在 iPhone 上验收：结局画面 → 暂停 → 重开 → 启动画面 → 开新一局；不得用运行时单元测试代替这一验收。
- 验证按键、音频、画面队列无残留；手动恢复前确认覆盖语义。
- 三端分别覆盖无存档、自动存档关闭、坏档、系统返回和前后台切换；测试使用隔离数据，不覆盖用户进度。
- 依变更范围执行仓库要求的 host、Android 单元/仪器、Harmony CTest/Hypium/连接设备安装、iOS runtime/UI 检查；不开展无关全平台扫测。
