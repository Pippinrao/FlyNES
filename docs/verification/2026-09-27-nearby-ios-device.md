## Harmony 房主 → iOS 客机

1. 相机识别邀请成功，首次连接 5 秒超时。用户开启系统“本地网络”权限后重扫，22:43:02 入房，原生加入约 214 ms。
2. 内置游戏与导入游戏均出现“本机没有该游戏”。诊断版复现内置游戏 `guestMatch rows=109 matched=0`。
3. 根因：Harmony / Android 内置游戏使用清单 `canonicalId` 作为联机键，iOS 游戏目录使用内容哈希 ID。iOS 客机原来直接按目录 ID 查清单键；iOS 房主反向也需要转换。
4. 修复：目录桥接提供双向转换，仅对内置来源与清单文件名匹配的条目转换；导入游戏保持内容 ID。本地读取、封面与存档仍使用原目录 ID；联机继续执行原生 ROM/config 哈希校验。
5. 修复包 23:13:06 在 iPhone 真机记录 `guestMatch matched=1`、进入 RUNNING；Harmony 同时运行《倾斜兄弟》，接收到 iOS P2 的非零按键及释放，超过 900 帧。截图显示 iPhone 已进入游戏模式菜单。此证据不代替双人对战、声音、暂停恢复和 iOS 房主真机验收。
6. 23:13:32 用户换到《雪人兄弟》，再次匹配不到。随后比对实际目录，确认属于游戏库缺少相同 ROM，见下节。

诊断最初使用 NSLog，实时与归档均未收到所需事件；改为现有原生模块使用的 os_log 后取得证据。日志只记录计数、状态、数值错误，不打印邀请或 ROM 内容。

## 9 月 28 日联机封面修复

- 根因：`RunSurfaceViewController` 只有单机分支调用 `captureCoverFrame`，而该方法只读取单机 `runtime_`；联机使用独立原生运行时。原房主房间测试通过辅助命令预写封面，只证明读取已有图片，未覆盖自动生成。
- 修复：联机播放提交画面时接入已有封面采样，从 nearby bridge 获取真实 RGB565 画面和帧号，继续以本地 canonical ID 存储，沿用现有采样时点与画面质量门槛。没有更改存档、ROM 或目录格式。
- 新增客机回归使用清单标注的封面测试 ROM，经真实原生对端配置并播放，从独立空封面目录验证产品自动保存图片，返回房间验证图片可见，再继续原进度。测试不调用预写封面的辅助命令，不修改产品的双人游戏筛选。
- 修复前该测试运行到第 1,786 帧仍没有封面，以明确断言失败；修复后包含新增测试、客机换游戏、房主回房间及双方继续的 UI 回归 **3/3 通过**（96.915 秒）。目录封面、播放及联机桥接运行时回归 **17/17 通过**（185.191 秒），包含 36,000 帧持续播放与反复暂停恢复。测试完成后的系统退出日志有 exit barrier 超时提示，XCTest 断言零失败，xcodebuild 返回 0。
- Mac 模拟器实际编译的本次产品文件与两个测试文件，按统一换行后的 SHA-256 对照本地工作区全部一致；记录在 `ios-cover-source-check.json`。
- 独立只读代码审查未发现需修改的问题。目录与三端一致性静态合同通过，内置内容门禁通过（7 个游戏）。证据日志：`ios-cover-red.log`、`ios-cover-green-ui.log`、`ios-cover-runtime.log`、`ios-cover-content-gate.log`。
